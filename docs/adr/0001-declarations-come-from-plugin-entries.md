# Declarations come from plugin entries

A plugin extends Ltix with entries, each a module and its options. A claim's URI and short name, a property's JSON name, a check's claim and message types, and every other declaration come from the entry's options. The one exception is a type's standard fields, because Elixir needs a struct's fields when the module compiles. One module can then serve many entries, the way one plug serves many pipelines, so a claim that only reads a JSON value with a Zoi schema needs no module of its own.

Plugins add these entries with functions on the provider they extend, such as `Ltix.Claim.add/2`, `Ltix.Launch.add_step/2`, and `Ltix.GradeService.LineItem.add_property/2`. What they add is an anonymous step, claim, check, override, or property. Each function is written by hand, with docs for its provider, and `use` generates none of them. A plugin writes a module when it needs more than a function or a Zoi schema, or when other plugins must refer to what it adds. Message types, requirements, conditions, and content item types are always modules, because each is built with its own DSL or defines a struct.

Ordering, overrides, and validator tags refer only to modules, so nothing can refer to an anonymous entry. A conflict lists the plugins involved and what they declare.

## Considered options

- **One module per declaration**, the original design. `use` fixed each module's declaration when it compiled, so two claims that differ only in data took two modules. Core had 19 claim modules that each held a URI, a short name, and a schema. Only struct fields and behaviours have to be known at compile time, so nothing required this.
- **Names for anonymous entries**, like a GenServer's `name:`. A step simple enough to be a function is too small for other plugins to order against or override, and a second kind of identity would exist for that case alone.
- **Functions generated by `use Ltix.Provider`**, such as an `add_property/2` on every provider whose hook includes `Ltix.Property`. It needed an exception for `Ltix.Claim`, and it hid public functions behind a macro.

## Consequences

- `use` options are fixed, and an entry that sets one again raises. A module's source always says what it declares.
- `Ltix.Plugin.add/2` validates an entry's options and raises `ArgumentError`. Conflicts are for contradictions between plugins.
- Each entry in a plugin set records the plugin that added it.
